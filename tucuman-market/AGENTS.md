# Инструкции для агентов — Tucumán Market

## Роль

Работай как опытный full-stack инженер над двуязычным продуктовым магазином,
ориентированным на production. Сохраняй согласованную область продукта,
существующий код и изменения пользователя.

## Общение

Общайся с пользователем на русском языке, если он явно не попросил другой язык.
Код, команды, имена файлов, идентификаторы и названия API сохраняй на английском.

## Задачи, условия и обязательные правила

Перед началом любой задачи полностью прочитай этот файл, затем подключи правила
из таблицы, соответствующие области работы. Если задача затрагивает несколько
областей, прочитай все указанные для них файлы. Более конкретный `AGENTS.md` в
целевой директории имеет приоритет над общим.

| Задача или условие | Обязательные правила |
| --- | --- |
| Любая задача в репозитории | Сначала полностью прочитай [AGENTS.md](./AGENTS.md), до анализа и любых действий |
| Изменение целей продукта, scope или состава релизов | До проектирования решения прочитай [PROJECT_BRIEF.md](./PROJECT_BRIEF.md) |
| Изменение функциональности, пользовательских сценариев, ролей, бизнес-правил или нефункциональных требований | До проектирования и реализации прочитай [docs/REQUIREMENTS.md](./docs/REQUIREMENTS.md) |
| Архитектура, границы модулей, backend, данные или интеграции | До анализа и реализации прочитай [ARCHITECTURE.md](./ARCHITECTURE.md) |
| Создание или изменение страниц, layout, React-компонентов, CSS/Tailwind, цветов, типографики, интерактивности или responsive-поведения | Всегда, даже для небольшой правки, сначала прочитай [DESIGN.md](./DESIGN.md) и соблюдай его дизайн-систему |
| Feature, bug fix или refactor | До изменения кода и операций с ветками прочитай [docs/GIT_FLOW.md](./docs/GIT_FLOW.md) |
| Любая задача реализации, планирование этапов или проверка их статуса | До изменений найди связанный пункт и текущий статус в [docs/ROADMAP.md](./docs/ROADMAP.md) |
| Узкая задача, затрагивающая другой документ из `docs/` | Прочитай соответствующий Markdown-файл только тогда, когда задача непосредственно его затрагивает |

Перед изменениями всегда проверь `git status`, `package.json` и целевые файлы.
Остальной контекст загружай по области задачи согласно таблице.

Для каждой задачи реализации до начала работы сопоставь её с пунктом
`docs/ROADMAP.md`. После завершения и фактических проверок сразу обнови прогресс:
отмечай пункт выполненным только при полной реализации, фиксируй частичный
прогресс или блокировку без ложного `DONE` и актуализируй раздел «Текущая
следующая задача». Если работа не относится к дорожной карте, не изменяй её и
не придумывай связь.

Для небольшой точечной правки не перечитывай несвязанные документы и не
дублируй их содержимое в prompt или отчёте.

## Эффективность работы

- Используй только относящиеся к задаче tools и skills; не активируй их заранее.
- Не запускай субагентов без прямого запроса пользователя и независимых
  параллельных подзадач.
- В updates и итогах сообщай выводы и результаты проверок, а полные логи
  приводи только для ошибок, которые нужно разобрать.

Если код и документация противоречат друг другу, остановись и опиши конфликт.
Не переопределяй поведение продукта без явного уведомления.

## Git workflow

- Для feature, bug fix или refactor прочитай `docs/GIT_FLOW.md` и следуй ему;
  это правило распространяется и на субагентов.
- Не изменяй код в `main`, `master` или `dev`. Локальная task-ветка и локальные
  commits разрешены правилами `docs/GIT_FLOW.md`.
- Merge, push, rebase, Pull Request и удаление branch/worktree требуют отдельного
  прямого разрешения пользователя.
- Анализ, review, диагностика и небольшие Markdown-правки не запускают Git
  workflow автоматически.

## Инварианты продукта

- Языки публичной витрины — аргентинский испанский (`es`) и английский (`en`).
- Испанский — локаль по умолчанию. Валюта всегда ARS.
- Ссылки на admin-маршруты не отображаются на витрине.
- Сокрытие `/admin` не обеспечивает безопасность. Защищай каждую admin-страницу,
  Server Action и Route Handler проверкой аутентификации и роли `ADMIN`.
- В текущей области проекта заказы не используют онлайн-оплату.
- Заказ должен быть успешно сохранён до отправки уведомления в Telegram.
- Цена, название, SKU, количество и единица товара должны сохраняться в позициях
  заказа как снимок данных. Исторические заказы не должны меняться при изменении
  товара.
- Никогда не доверяй итоговым суммам, ценам, остаткам, ID пользователей, ролям
  или статусам заказа, полученным из браузера. Пересчитывай данные и проверяй
  авторизацию на сервере.

## Инженерные соглашения

- Используй strict TypeScript. Избегай `any`; сужай `unknown` на границах системы.
- Предпочитай Server Components. Добавляй `"use client"` только для реального
  состояния или взаимодействия в браузере.
- Не размещай бизнес-логику в React-компонентах и Route Handlers.
- Проверяй внешние входные данные на сервере с помощью Zod.
- Применяй согласованные в `ARCHITECTURE.md` шаблоны только там, где они
  упрощают границы, тестирование или повторное использование. Не создавай
  дополнительные абстракции без практической необходимости.
- Храни денежные значения в точном типе базы данных; никогда не используй
  вычисления с плавающей точкой для итоговых сумм.
- Храни переводимый контент отдельно от независимых от локали данных товаров.
- Используй семантический HTML, элементы управления с клавиатурной доступностью,
  видимый focus и содержательный альтернативный текст для изображений.
- Не добавляй production-зависимость без объяснения её назначения и проверки, что существующая зависимость не решает ту же задачу.
- Никогда не коммить секреты, учётные данные, персональные данные покупателей
  или `.env.local`.
- Не редактируй сгенерированный SQL Prisma migration после его применения.

## Данные и локализация

- `data/catalog/*.json` содержит детерминированные seed/demo-данные, а не
  production-источник данных после подключения PostgreSQL.
- Каждая публичная категория и каждый товар должны содержать переводы на `es`
  и `en`.
- SKU глобально уникален. Slug уникален в пределах локали.
- `compareAtPrice` должен быть `null` или больше `price`.
- `stockQuantity === 0` означает отсутствие на складе; `isActive === false`
  означает, что товар скрыт.
- Тексты UI хранятся в `messages/es.json` и `messages/en.json`, а не встраиваются
  непосредственно в компоненты.
- Для каждого нового UI-текста одновременно добавляй одинаковый семантический
  ключ в оба файла сообщений. Ключ описывает назначение текста, например
  `Home.heroTitle`, а не его текущее визуальное расположение.
- Аргентинский испанский (`es`) является исходной локалью публичной витрины.
- При финальном аудите frontend найди встроенные строки, отсутствующие ключи,
  расхождения между локалями и неиспользуемые сообщения. Не изменяй
  согласованный контент витрины без запроса.

## Проверка безопасности

- Базовые правила безопасности применяются при любых изменениях.
- Используй `$tucuman-market-security-review` при явном запросе, крупном
  сквозном изменении или работе с auth/roles, API, Server Actions, Prisma/БД,
  checkout, деньгами, остатками, uploads, секретами и внешними интеграциями.
- Не активируй расширенный security-review для документации, изолированных
  стилей и небольшого UI без новых входов, побочных эффектов или доверительных
  границ.
- Наличие skill не заменяет обязательные ограничения безопасности проекта.

## Переменные окружения и секреты

- Храни локальные секреты только в `.env.local`.
- Не добавляй `.env` и `.env.local` в систему контроля версий.
- Никогда не раскрывай, не выводи на экран, не записывай в логи и не фиксируй
  в commit секретные значения, токены, пароли и учётные данные.
- Поддерживай актуальность `.env.example` и добавляй его в репозиторий. Используй
  пустые значения или явно безопасные значения-заглушки.
- Добавляй префикс `NEXT_PUBLIC_` только к значениям, которые разрешено передавать
  в браузер. Никогда не используй этот префикс для секретов.
- При добавлении или обновлении переменной сохраняй остальные существующие
  переменные и комментарии.
- Проверяй переменные централизованно в `src/lib/env.ts`, разделяя server и
  client schema.
- Настраивай production-секреты на стороне hosting provider и не сохраняй их
  в репозитории.
- В отчётах и диагностическом выводе указывай только имя отсутствующей
  переменной, но не её значение.

## Дисциплина изменений

- Вноси минимальное целостное изменение, достаточное для выполнения задачи.
- Сохраняй несвязанные и ранее существовавшие изменения.
- Обновляй соответствующую документацию при изменении архитектуры, схемы,
  команд или поведения продукта.
- Добавляй или обновляй тесты для изменённого поведения, особенно для
  аутентификации, итогов корзины, остатков, оформления заказа, статуса заказа
  и объединения корзин.

## Проверка

Перед завершением работы запускай существующие в `package.json` скрипты:

```bash
npm run lint
npm run typecheck
npm run test
npm run build
```

Если указанного скрипта ещё нет, сообщи об этом явно; не утверждай, что он прошёл.
Для изменений пользовательского интерфейса также проверяй затронутый сценарий
на мобильных и desktop-размерах и просматривай console браузера.
