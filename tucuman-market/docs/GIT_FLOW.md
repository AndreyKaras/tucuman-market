# Жизненный цикл задач и Git workflow

Этот документ определяет безопасный Git workflow для разработки Tucumán Market.
Он применяется к реализации новой feature, исправлению bug и refactor. Анализ,
review, диагностика, браузерная проверка и небольшие изменения только
документации не запускают этот workflow автоматически.

Запрос пользователя на реализацию feature, fix или refactor является постоянным
разрешением только на создание локальной task-ветки и локальных атомарных
commits внутри неё. Он не разрешает merge, push, rebase, создание Pull Request,
удаление ветки или worktree.

## 1. Предварительная проверка

До создания ветки или изменения файлов:

1. Прочитать глобальные и ближайшие проектные `AGENTS.md`, `PROJECT_BRIEF.md`,
   `ARCHITECTURE.md` и относящиеся к задаче документы из `docs/`.
2. Определить Git root, текущую ветку и состояние worktrees:

   ```bash
   git rev-parse --show-toplevel
   git branch --show-current
   git status --short --branch
   git worktree list
   ```

3. Проверить `package.json` и относящиеся к задаче конфигурационные файлы.
4. Определить, принадлежат ли уже существующие изменения текущей задаче.

Git root проекта находится уровнем выше Next.js-приложения. Основной код и
документация расположены в каталоге `tucuman-market/` внутри worktree. При
создании нового worktree рабочим каталогом приложения будет соответственно
`<worktree>/tucuman-market`.

### Незавершённые изменения

- Не удалять, не перезаписывать и не коммитить существующие изменения, которые
  не были созданы текущим агентом в рамках задачи.
- Не выполнять автоматически `git stash`, `git reset`, `git checkout --`,
  `git restore`, очистку untracked-файлов или перенос изменений между ветками.
- Если рабочая директория содержит несвязанные изменения и безопасно отделить их
  нельзя, остановиться до редактирования и запросить решение пользователя.
- Если все незавершённые изменения точно принадлежат той же продолжающейся
  задаче, их можно перенести в создаваемую task-ветку только после явной проверки
  полного diff.

## 2. Защищённые ветки

Текущая основная ветка проекта — `main`. Ветки `main`, `master` и `dev`, если
они существуют, считаются защищёнными.

- Не изменять исходный код непосредственно в защищённой ветке.
- Не создавать feature/fix/refactor commits в защищённой ветке.
- Не выполнять merge в защищённую ветку без прямого ответа пользователя
  `Да, сливай`.
- Не выполнять push защищённой или task-ветки без отдельного прямого запроса.

Небольшие изменения только Markdown-документации могут выполняться в текущей
ветке, но commit для них по-прежнему требует явного запроса пользователя, если
они не являются частью уже авторизованной feature/fix/refactor-задачи.

## 3. Названия веток и commits

Использовать короткий английский kebab-case без пробелов и кириллицы.

| Тип работы | Ветка | Commit |
|---|---|---|
| Новая функциональность | `feat/<task-slug>` | `feat: ...` |
| Исправление ошибки | `fix/<task-slug>` | `fix: ...` |
| Refactor без изменения поведения | `refactor/<task-slug>` | `refactor: ...` |
| Документация | `docs/<task-slug>` | `docs: ...` |
| Тесты | `test/<task-slug>` | `test: ...` |
| Инфраструктура и обслуживание | `chore/<task-slug>` | `chore: ...` |
| Build или CI | `build/<task-slug>` / `ci/<task-slug>` | `build: ...` / `ci: ...` |

Допустим необязательный scope, например `feat(catalog): add product repository`.
Сообщение commit пишется на английском, в повелительной форме и описывает один
логический результат.

## 4. Выбор режима изоляции

### Сценарий A — параллельная работа

Использовать Git worktrees, если:

- несколько агентов или процессов одновременно изменяют файлы проекта;
- задачи делегированы субагентам для параллельной реализации;
- в основном рабочем каталоге уже выполняется другой процесс, который записывает
  изменения в те же файлы или Git index.

Каждый параллельный исполнитель получает:

- отдельную task-ветку;
- отдельный worktree в разрешённом для записи и заранее проверенном каталоге;
- рабочий каталог `<worktree>/tucuman-market`;
- конкретную область файлов и ответственность;
- запрет изменять или коммитить файлы другого исполнителя.

До `git worktree add` проверить абсолютный путь назначения. Не размещать
worktree поверх существующего каталога и не удалять его автоматически. Типовая
команда после выбора безопасного пути:

```bash
git worktree add -b feat/<task-slug> <absolute-worktree-path> main
```

Если задача начинается не от `main`, явно зафиксировать выбранную base-ветку в
отчёте. Один и тот же branch нельзя использовать одновременно в нескольких
worktrees.

### Сценарий B — одиночная последовательная работа

Если изменения вносит один исполнитель и нет другого конкурентного writer,
создать task-ветку в текущем worktree:

```bash
git switch -c feat/<task-slug>
```

Префикс команды заменить в соответствии с типом задачи. Перед переключением
ветки обязательно разрешить вопрос с существующими незавершёнными изменениями.

Запущенный read-only dev server или тестовый процесс сам по себе не требует
worktree. Изоляция обязательна при конкурентной записи файлов или Git index.

## 5. Разработка и атомарные commits

Работать итеративно внутри своей task-ветки и worktree.

Логический блок считается готовым для автоматического локального commit, когда:

- он предоставляет целостный проверяемый результат;
- относящиеся к блоку тесты и проверки прошли либо отсутствие проверки явно
  объяснено;
- staged diff просмотрен полностью;
- staged diff не содержит секретов, `.env`, `.env.local`, персональных данных,
  generated build output и несвязанных пользовательских изменений;
- commit не оставляет заведомо сломанную сборку или полуреализованный контракт.

Примеры самостоятельных блоков:

- Prisma schema и первоначальная migration;
- repository вместе с относящимися к нему integration tests;
- законченный Server Action с валидацией и тестами;
- самостоятельный UI-компонент со всеми required states;
- исправление bug и regression test.

Для небольшой задачи достаточно одного финального commit. Не создавать commits
по времени, количеству строк или после каждого файла.

### Безопасный staging

- Добавлять только явно перечисленные файлы текущего блока.
- Не использовать `git add .`, `git add -A` и широкие glob-паттерны в грязной
  рабочей директории.
- Перед каждым commit выполнять:

  ```bash
  git status --short
  git diff --check
  git diff --cached --check
  git diff --cached
  ```

- Если в staged попал несвязанный файл, удалить только его из index безопасной
  недеструктивной командой, не изменяя содержимое рабочей копии.
- Не изменять и не переписывать уже созданные commits без прямой необходимости
  и разрешения. Не использовать `--amend` для сокрытия чужих изменений.

### Проверки

Запускать только существующие scripts из `package.json` и относящиеся к блоку
проверки. В текущем проекте ожидаются:

```bash
npm run lint
npm run typecheck
npm run test
npm run build
```

Если script ещё не существует или проверка заблокирована внешним условием,
сообщить об этом явно. Не утверждать, что незапущенная проверка прошла.

Для изменений Prisma дополнительно проверить migration SQL, seed, constraints и
выполнить применимые database tests. Для значимых UI-изменений проверить mobile,
desktop, browser console и horizontal overflow.

## 6. Работа субагентов

- Каждый субагент обязан прочитать `AGENTS.md` и этот документ перед записью.
- Субагент работает только в назначенном worktree и переданной области файлов.
- Субагент не переключает общие ветки, не переносит commits других исполнителей
  и не выполняет merge, push, rebase или удаление worktree.
- Перед началом координатор сообщает branch, абсолютный worktree path, base-ветку
  и ожидаемый результат.
- После завершения субагент сообщает commit SHA, изменённые файлы, выполненные
  проверки и известные ограничения.
- Координатор проверяет каждый commit и разрешает конфликты только в собственной
  integration/task-ветке. Коммиты не переносятся в `main` без разрешения
  пользователя.

## 7. Завершение задачи

После выполнения требований:

1. Запустить все доступные относящиеся к задаче проверки.
2. Просмотреть изменения task-ветки относительно base-ветки.
3. Убедиться, что рабочая директория содержит только ожидаемые изменения.
4. Создать финальный локальный commit, если после последнего атомарного commit
   остался законченный проверенный блок.
5. Остановиться, не выполняя merge, push, PR или удаление worktree.

Финальный отчёт содержит:

- branch и использованный сценарий изоляции;
- список commits с SHA и сообщениями;
- изменённые файлы и реализованное поведение;
- выполненные проверки и их результат;
- незапущенные проверки, ограничения и остаточные риски;
- состояние `git status`.

Для сценария B завершить вопросом:

> Фича реализована. Проверяем работу, или я могу выполнить слияние (merge) с
> главной веткой?

Для сценария A завершить вопросом:

> Изолированная работа завершена. Могу ли я слить ветку в `main` и удалить
> временный worktree?

Только прямой ответ пользователя `Да, сливай` разрешает выполнить предложенный
merge и, для сценария A, удалить соответствующий временный worktree. Это не
является разрешением на push или создание Pull Request.

## 8. Строгие запреты без прямого разрешения

- `git merge`, включая merge в защищённую ветку;
- `git push` и особенно force push;
- `git rebase`, `git cherry-pick` и переписывание истории;
- создание или отправка Pull Request;
- удаление branch или worktree;
- автоматический stash пользовательских изменений;
- destructive команды `git reset --hard`, `git clean`, `git checkout --` и
  эквивалентные операции;
- commit секретов, `.env`, `.env.local`, персональных данных и несвязанных
  изменений.
